Retry scheduling for
UPI AutoPay subscriptions

Indian subscription payments are collected by a standing mandate on UPI. When the account is short on the due date the debit is declined, and the usual response is to retry on the following days. This agent treats each decline as a measurement of the customer's balance, estimates when the salary arrives, and schedules the attempt for a day the money is likely to be there.

90.41% collected by a simple payday baseline

A difference of +8.70 percentage points, 2 SE 0.68 across populations, measured at payday_err=±7 and pop_spend=0.93. It is a curve in both of those, not a constant: across the plausible range of household spending it runs from +0.89 to +8.70. A fixed two-attempt schedule collects more than the agent when payday is already known to within three days. Repeating the run on four different random seeds moves the difference by 1.89 points, which the interval above does not include. The populations are held out, the sample size was chosen by running the same experiment at five sizes, and one command reproduces every figure on this page.

The waiting decision

Each day the agent compares two numbers: the chance the debit clears tomorrow, and the best chance available on any remaining day of the cycle. On day 16 it has seen nothing this cycle and rates those 92% and 97%, so it attempts. After the decline they are 15% and 96%, and it holds. Only four attempts are available for the whole cycle, so an attempt against an empty account is wasted.

Where the agent fails on this customer

At ±10 or ±14 days of payday uncertainty the agent misses this customer's cycle entirely: all three attempts land before the salary and decline. Two other customers in the same population that it also fails to collect from are named in scripts/build_page_data.py.

This customer holds two subscriptions and receives one salary credit a month. The arrows and decisions come from agent runs at six levels of payday uncertainty on held-out population 710 — one of the ten the batch result above is measured on — stored in docs/data/scenarios.json.

03

How the agent works

Once a day, for every live mandate. A declined ₹550 charge means the balance was below ₹550 at that moment; a successful one means it was at least ₹550. Accumulated over attempts, these bounds give an estimate of both the balance and the salary date.

The daily loop

  1. Track the belief. One probability distribution per customer, covering the balance and which day of the cycle the salary lands. All of a customer's subscriptions share it.
  2. Compare today with later. If a later day has a better chance, wait.
  3. Diagnose the failure. Name a cause and pick an action: retry, nudge, escalate, stop.
  4. Check the action is legal against five mandate rules.
  5. Execute or refuse. Refused actions never reach the payment rail. After the first or second insufficient-funds decline, a funding reminder is sent. After the third, a Payment Link replaces the fourth mandate debit so that debit is not fired.
  6. Fold the outcome back in, success or decline.
  7. Log everything, including the days it chose to do nothing.

Enforced boundaries

The language model cannot pick the debit time. It explains why a payment failed and chooses between interventions. The data type it returns has no field for a time, and an import-graph check prevents that layer from importing the timing code, the balance estimate or the executor.

The constraint layer refuses; a separate auditor recounts. One component blocks illegal actions. A second rebuilds what was legal from the audit log, using code that cannot import the first. Both counts are printed side by side. Over 44,271 money actions in the headline batch, both are zero.

Each rule is enforced by the agent and covered by a test in both the agent and the simulation. The rules are second-hand summaries of NPCI's requirements rather than a regulation read end to end.

Error handling

The rule-engine fallback is the normal path: the batch takes it on about 95% of decisions by design.

What failsWhat happens
The language model errors, times out, or returns something unparseable Falls back to a deterministic rule engine and records that it did. The headline number therefore does not depend on an API key.
The model returns an instruction containing a time Rejected — and the data type it returns has no field for a time in the first place.
An action would breach one of the five mandate rules Refused before the payment rail is reached, with the refusal written to the audit log. A refused action generates no network traffic at all.
The payment rail is down across many customers at once Detected from cross-customer outcomes, and the balance estimate is left alone. A technical decline is a fact about the rail, not about one customer.
A debit's result is genuinely unknown — a timeout, a deemed transaction Recorded as unknown, never as a failure. Rounding an unknown down to "failed" is what licenses a retry, and a retry on an unknown is a double charge.
A request is retried after a network failure The idempotency key comes from the action id already written to the audit log, so the same logical debit produces the same key across a restart.
Razorpay rejects the request itself — bad credentials, malformed body Raises, naming the HTTP status and the response. A request-level rejection is not recorded as a customer decline, because no payment was created.
A worker process dies during a measurement The measurement fails loudly. A crashed run is a failed result, not a missing one.
A second run appends to an existing audit log Refused when the log is opened, so one log always describes exactly one run.
04

Outage detection

An empty account and a degraded payment network both produce a failed debit, and the balance estimate cannot distinguish them. During a rail outage every affected customer's estimate is updated with a decline that says nothing about their balance. The agent detects this by tracking the failure rate across all customers at once.

Three decision hours from one 120-day run

Each shows the attempts the agent saw in the previous 24 hours.

What the agent saw
failed for a technical reason every other attempt
What it concluded

Four six-hour outages were injected on days 20, 50, 80 and 110, each removing about 40% of attempts. No source reports what fraction of AutoPay debits fail during a UPI incident, so that severity is swept across three values rather than chosen. In a separate study containing no outages, the detector raised a false alarm in 0 of 48 runs. The alarm shown above comes from a single run of a horizon that does contain outages; the two are different measurements. Where an outage is present, the detector catches it in 0.75 of runs at 100 customers and all of them at 200. Transcript logs/w30_detect_study.txt.

This panel runs the world the outage measurements are made in — 100 customers holding five mandates each at pop_spend=1.05 — and not the world the batch figure above uses. That world was chosen because it has the attempt volume to show where the detector starts working, which is what this panel is for.

Measured on the world the batch figure does use, 500 customers holding about two subscriptions each carry 38.5 attempts per 24-hour window against the detector's floor of eight, and every injected outage at severity 0.40 is caught. At 100 customers that world averages 7.6 attempts per window — just under the floor — and the detector still fires in 0.70 of runs, because individual windows run above the mean. Transcript logs/w30_detect_canonical.txt.

Pausing during a detected outage

Pausing dispatch during a detected outage is worth a fifth of a point at the worst severity tested, and less below it, measured across 10 populations. The effect is small because pausing costs a scheduling day whether or not the rail is actually degraded, and most of the day's attempts have already been sent by the time enough evidence accumulates.

Pausing is off by default. The shipped behaviour is detection plus a change to how declines are folded into the balance estimate. The gain grows with severity and clears its error bar at every severity above zero, but the threshold written down in advance for shipping it was more than one point, and the largest measured gain is +0.221. Effect of pausing on detection

A paused attempt produces no result, and the detector counts results. In the run shown above, pausing removed enough attempts that the agent detected one outage window instead of two.

05

Merchant-level and pooled data

A single merchant charges a customer once a month and so observes one attempt per customer per month. An aggregator carrying that customer's other subscriptions observes more. Estimating payday and detecting an outage both depend on attempt volume, and how much more an aggregator observes depends on how many subscriptions a customer holds. The agent keeps one belief state per customer, shared across that customer's subscriptions, and what that sharing is worth is measured below.

Attempts per 24-hour window

The mandates in this population are spread over 60 merchants. The outage test requires at least 8 attempts in the window.

The vertical mark on each bar is the eight-attempt floor. Below it the agent does not evaluate the outage test. Transcript logs/w30_detect_study.txt.

Effect on collection rate

The sharing is implemented and switchable, so its value is measured rather than argued. Running fully unpooled — each merchant estimating the same customer separately — costs 0.16 percentage points (±0.16) in the world the headline above is measured in, about two subscriptions per customer. That is not distinguishable from zero. The same measurement in a world where every customer holds five subscriptions costs 6.47 points (±0.62) at pop_spend=1.05 and 1.30 (±0.42) at 0.80.

Pooling pays in proportion to how many subscriptions a customer holds. Published aggregates — about 95 million active AutoPay mandates against a UPI base past 500 million users — put the mean between one and three, and this simulation uses two. No source gives the distribution itself, so the exact 1 + Poisson(1) draw is a modelling approximation. How much turns on the count is measured rather than assumed: the five-subscription figure above is that same measurement above the top of the derived range. The case for running this at an aggregator rather than at a merchant is conditional on that count. Transcripts logs/w30_pooling_canonical.txt and logs/w30_pooling_gateworld.txt.

Pooling is a per-customer permission, so an operator can switch it off per customer without changing anything else. Pooling only for consenting customers costs 2.77 points at half consent in the five-subscription world, and 0.07 in the canonical one.

Bank-level outages

Customers are spread across eight banks. An incident at one bank lifts the pooled failure rate by roughly an eighth of its severity, which is below the detection threshold. Pooling hides outages confined to a single bank.

200 customers, four windows, 8 populations. Share of outage windows detected. Transcript logs/w27_decline_sweep_repaired.txt.

Legal status

Whether cross-merchant pooling — a payment aggregator using one merchant's transaction outcomes to schedule another merchant's debit for the same customer — is lawful in India has not been established either way. The treatment is jurisdiction- and provider-dependent and is a question of law, outside the scope of this engineering evaluation. No statute or circular addresses the scenario directly; Razorpay's merchant terms, their privacy policy and the relevant RBI directions have not been read. The engineering response is to make pooling a per-customer permission, which is not a legal conclusion.

07

External validation

There is no public benchmark for payment retry scheduling: no shared dataset, no held-out set, no leaderboard. The available comparisons are aggregate statistics published by companies selling recovery software. They are second-hand and they aggregate customer bases that are not comparable. The simulation is scored against four of them below.

Four published figures

The simulation is calibrated against a single anchor. None of the four below was used to set a parameter.

The two matches

The two come from different parts of the model. The first measures the simulated world: how often an account is short on the due date. The second measures a baseline policy running inside it: what Razorpay's documented T, T+1, T+2, T+3 schedule recovers. Both fall inside their published bands at the same calibration.

The second row is also what answers the third. Both are measured in the same world, at the same calibration, with the same run seed. A world calibrated to be easy would lift both. The second lands in band and the third sits above it, so the excess belongs to the agent rather than to the world. That reading fails if the second row drops below 20% at a larger sample, or holds only at a calibration where the first leaves its own band.

The two mismatches

Recovery is too high because no simulated customer is permanently unable to pay: a clairvoyant schedule obeying the same four-attempt cap and notice rules collects 100% here, so that row measures the agent rather than the world. Recovery is too slow because a mandate's due date and its customer's payday are drawn independently, so the gap between them averages half a cycle. The same clairvoyant schedule reaches only 51.9% of failed debits inside ten days, below the published band's floor; the agent reaches 82.6% of that. The two rows have separate causes.

Alternative calibrations

Adding customers who cannot pay brings the third row inside its band, and so does adding temporary account holds. Both were swept, and both moved the first row outside its band. A grid search found a cell satisfying two targets at once; at that cell the two targets it had not been tuned against both moved outside their bands. Fourteen alternative calibrations have been swept and none scores better against the four figures than the one reported here.

Transcripts logs/w7_rerun.txt (transient holds) and logs/w2_rerun.txt (insolvency). Both were measured on an earlier experimental world and are quoted here for the direction of the sweep rather than for its levels. The full results name them.

Limits of this comparison: the published figures are vendor material rather than ground truth, and a simulation can reproduce an aggregate statistic while modelling the underlying mechanism incorrectly. Four figures is a small set; five further targets are specified but not yet implemented.

08

Scope

No Razorpay transaction, mandate or decline code has been observed by this project. All percentages and rupee totals here come from simulation. The simulation and the agent share an author, so the results are not independent evidence and should not be read as production estimates.

Simulated

  • Customer balances, salaries and spending
  • Payday timing
  • Every debit outcome
  • Outage windows and their severity
  • The merchant population
  • Every percentage and rupee figure here

From published sources

  • NPCI's five mandate execution rules
  • NPCI's decline code list and what each code means
  • Razorpay's 110 published error reasons
  • Razorpay's documented retry schedule (T, T+1, T+2, T+3, then halt)
  • The shape of Razorpay's Payment Downtime API

Not established by this project

  • How often each decline reason actually occurs — every rate is swept rather than chosen
  • How accurately payday can be predicted in India — swept from ±1 to ±14 days
  • What fraction of debits fail during a UPI incident — severity is swept
  • The distribution of AutoPay mandates one customer holds. Published aggregates put the mean between one and three; the exact draw is a modelling approximation
  • Whether Razorpay's API accepts the recurring-charge request body written here. The client authenticates against the test API and reads successfully; charging requires an authorised mandate, which this test account cannot register
  • The legal treatment of cross-merchant pooling, which is a question of law and outside the scope of this evaluation

Limitations

  • The headline depends on two parameters, and both are swept rather than assumed. The +8.70 point figure is measured under a ±7-day payday-error regime; at ±1 day the agent and the baseline are level. It also depends on spending pressure: the difference runs +0.89 to +8.70 across the plausible range of household spending, and at the gentle end of that range the world produces few enough failed debits that the row is a thin measurement — 49 of them at pop_spend=0.80, across five thousand customers.
  • Every figure here is one random seed, and the interval beside it does not say so. The 2 SE quoted with the headline is the spread across the ten populations. Running the identical experiment on four different run seeds moves the difference between the agent and the baseline by 1.89 points — from +7.38 to +9.26 — and almost all of that movement is the baseline, which waits for a payday estimate the seed draws. The agent's own collection moves by 0.18 points.
  • A fixed schedule beats the agent when payday is predictable. Two attempts placed at frozen offsets from the same payday estimate the agent is given collect 99.89% of at-risk cycles at ±1 day, against the agent's 97.90%. The agent is behind by 2.00 points there and by 1.62 at ±3, both by more than the paired measurement error, level at ±5, and ahead by 2.16 at ±7, 20.05 at ±10 and 33.90 at ±14. The fixed schedule also loses no mandates at any level tested — 100.0% survival against the agent's 99.0–99.5%. Transcript logs/w30_steelman_n500.txt. How accurately payday can be estimated in India is unmeasured, and Indian payroll practice — statutory payment by the 7th or 10th, most firms on the last working day, government salaries on a fixed date — points at the predictable end, where the fixed schedule is the simpler choice. The agent's advantage is protection against that estimate being wrong.
  • The headline batch runs with the richer decline taxonomy switched off, so it contains no frozen accounts, revoked mandates or limit hits. The taxonomy is implemented and its cost is measured: switching it on costs between 0 and 13.5 points across the swept range. No source publishes those rates, which is why they are swept rather than set.
  • The largest single sensitivity is a rate nobody publishes. How often a debit is refused by a transaction or mandate limit is not published anywhere, so it is swept rather than chosen. The curve is non-linear, so the midpoint of the range is not the midpoint of the cost.
  • The timing score contains a hand-chosen discount factor. Sweeping it from 0.80 to 1.00 on the shipping filter moves recovery by 3.9 points, from 91.3% to 95.2%. The shipped 0.92 is not the best cell on that grid — 0.88 scores 0.44 points higher — and the constant was not re-selected against it.
  • Four of the simulation's twenty-seven checks fail on a clean checkout. Each has a written reason recorded rather than a loosened threshold. Two are calibration gates that no parameter fixes; two are controls left failing so that a rewrite of the surrounding tests remains auditable. They are diagnostics on specific properties and the other twenty-three gates pass unchanged.
  • Simulation results are not production estimates. The published industry benchmark for retry optimisation is a 6–8% uplift. The +8.70 point figure describes this simulated world at pop_spend=0.93.
  • Two of the four external checks are missed, and one of them cannot be hit on this rail. A clairvoyant schedule obeying the same four-attempt cap and notice rules reaches only 51.9% of failed debits inside ten days, against a published band of 85–95% drawn from card dunning. The agent reaches 42.9%, or 82.6% of what is available.
  • The study is small: 500 customers, about 2 mandates each, 10 populations for the batch figure and 20 for the external checks, one run seed each. The sample size was chosen by running the same experiment at 100, 250, 500, 1,000 and 2,000 customers; 500 sits within 0.19 points of 2,000 on the headline difference.
  • The belief is not well calibrated. Two of the four failing checks are calibration gates: the filter's diffusion leaks through the balance floor it does model, so it can believe money appeared where none did. A repair exists, is measured, and is off because it kills more mandates at this horizon.
  • The constraint layer and the live Razorpay executor keep two different clocks for the same field, so the live executor has not been driven end to end by the constraint layer with a genuine order. A committed proof script asserts the refusal rather than working around it.
  • The single-customer walkthrough in section 01 is one customer. It comes from the same world and the same held-out population as the batch figure, and it is chosen for legibility rather than for being typical or flattering. The three mandates in the same population that the agent attempts at least three times and never collects are named in the repository.
