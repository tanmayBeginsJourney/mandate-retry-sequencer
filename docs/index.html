Retry scheduling for
UPI AutoPay subscriptions

Indian subscription payments are collected by a standing mandate on UPI. When the account is short on the due date the debit is declined, and the usual response is to retry on the following days. This agent estimates when the salary arrives and schedules the attempt for a day the balance is likely to cover it.

The waiting decision

Each day the agent compares two numbers: the chance the debit clears today, and the best chance available on any remaining day of the cycle. On day 4 those are 12% and 31%, so it holds the attempt. Only four attempts are available for the whole cycle, so an attempt against an empty account is wasted.

Where the agent fails on this customer

At ±10 or ±14 days of payday uncertainty the agent misses this customer's cycle: it waits past the salary credit and both remaining attempts decline. Two other customers in the same population where it performs worse are named in scripts/build_page_data.py.

This customer has a flat balance, one salary credit and one debit. The arrows and decisions come from agent runs at six levels of payday uncertainty, stored in docs/data/scenarios.json.

03

How the agent works

Once a day, for every live mandate. A declined ₹550 charge means the balance was below ₹550 at that moment; a successful one means it was at least ₹550. Accumulated over attempts, these bounds give an estimate of both the balance and the salary date.

The daily loop

  1. Track the belief. One probability distribution per customer, covering the balance and which day of the cycle the salary lands. All of a customer's subscriptions share it.
  2. Compare today with later. If a later day has a better chance, wait.
  3. Diagnose the failure. Name a cause and pick an action: retry, nudge, escalate, stop.
  4. Check the action is legal against five mandate rules.
  5. Execute or refuse. Refused actions never reach the payment rail. After the first or second insufficient-funds decline, a funding reminder is sent. After the third, a Payment Link replaces the fourth mandate debit so that debit is not fired.
  6. Fold the outcome back in, success or decline.
  7. Log everything, including the days it chose to do nothing.

Enforced boundaries

The language model cannot pick the debit time. It explains why a payment failed and chooses between interventions. The data type it returns has no field for a time, and an import-graph check prevents that layer from importing the timing code, the balance estimate or the executor.

The constraint layer refuses; a separate auditor recounts. One component blocks illegal actions. A second rebuilds what was legal from the audit log, using code that cannot import the first. Both counts are printed side by side. Over 8,832 money actions in the headline batch, both are zero.

NPCI mandate rules enforced

RuleWhat it requires
Attempt capAt most 4 attempts per mandate per billing cycle

Notice periodAt least 24 hours between the pre-debit notice and the debit
One pending noticeOnly one outstanding notification per mandate
No re-presentationAn insufficient-funds decline may not be retried under the old notice

Each rule is enforced by the agent and covered by a test in both the agent and the simulation. The rules are second-hand summaries of NPCI's requirements rather than a regulation read end to end.

Error handling

The rule-engine fallback is the normal path: the batch takes it on about 95% of decisions by design.

What failsWhat happens
The language model errors, times out, or returns something unparseable Falls back to a deterministic rule engine and records that it did. The headline number therefore does not depend on an API key.
The model returns an instruction containing a time Rejected — and the data type it returns has no field for a time in the first place.
An action would breach one of the five mandate rules Refused before the payment rail is reached, with the refusal written to the audit log. A refused action generates no network traffic at all.
The payment rail is down across many customers at once Detected from cross-customer outcomes, and the balance estimate is left alone. A technical decline is a fact about the rail, not about one customer.
A debit's result is genuinely unknown — a timeout, a deemed transaction Recorded as unknown, never as a failure. Rounding an unknown down to "failed" is what licenses a retry, and a retry on an unknown is a double charge.
A request is retried after a network failure The idempotency key comes from the action id already written to the audit log, so the same logical debit produces the same key across a restart.
Razorpay rejects the request itself — bad credentials, malformed body Raises, naming the HTTP status and the response. A request-level rejection is not recorded as a customer decline, because no payment was created.
A worker process dies during a measurement The measurement fails loudly. A crashed run is a failed result, not a missing one.
A second run appends to an existing audit log Refused when the log is opened, so one log always describes exactly one run.
04

Outage detection

An empty account and a degraded payment network both produce a failed debit, and the balance estimate cannot distinguish them. During a rail outage every affected customer's estimate is updated with a decline that says nothing about their balance. The agent detects this by tracking the failure rate across all customers at once.

Three decision hours from one 120-day run

Each shows the attempts the agent saw in the previous 24 hours.

What the agent saw
failed for a technical reason every other attempt
What it concluded

Four six-hour outages were injected on days 20, 50, 80 and 110, each removing about 40% of attempts. No source reports what fraction of AutoPay debits fail during a UPI incident, so that severity is swept across three values rather than chosen. In a separate study containing no outages, the detector raised a false alarm in 0 of 48 runs. The day-67 alarm above comes from a single run of a horizon that does contain outages; the two are different measurements.

Pausing during a detected outage

Pausing dispatch during a detected outage reduces collection at moderate severity, measured across 8 populations. It costs a scheduling day whether or not the rail is actually degraded, and most of the day's attempts have already been sent by the time enough evidence accumulates.

Outage severityPausing is worth2 SE

Pausing is off by default. The shipped behaviour is detection plus a change to how declines are folded into the balance estimate. Measured on the current simulation, pausing is worth nothing the experiment can distinguish from zero: 0.000 points at the two lowest severities, +0.017 and +0.051 at the two highest, every one of them inside its own error bar.

Effect of pausing on detection

A paused attempt produces no result, and the detector counts results. In the run shown above, pausing removed enough attempts that the agent detected one outage window instead of two.

One run, no error bars. The recovery difference is consistent with the 8-population measurement on the left but does not replicate it.

05

Merchant-level and pooled data

A single merchant charges a customer once a month and so observes one attempt per customer per month. An aggregator carrying that customer's other subscriptions observes five. Estimating payday and detecting an outage both depend on attempt volume.

Attempts per 24-hour window

The mandates in this population are spread over 60 merchants. The outage test requires at least 8 attempts in the window.

The vertical mark on each bar is the eight-attempt floor. Below it the agent does not evaluate the outage test.

Effect on collection rate

Sharing one estimate across a customer's subscriptions, instead of each merchant estimating that customer separately, is worth +7.32 percentage points (±2.02) at pop_spend=1.05 on the shipping filter (gate S2a_PD) and +1.30 (±0.42) at 0.80, the calibration whose failure rate matches the published band. The 0.80 figure is an agent measurement, not gate-protected. The value varies with world hardness by a factor of five, so the hard-world number on its own is not the value of pooling.

The legal position on sharing one customer's outcomes across merchants is unsettled, so pooling is a per-customer permission. Pooling only for consenting customers costs 2.77 points at half consent at pop_spend=1.05, and 0.57 at 0.80. Re-measured 1 September 2026 after the payday prior was re-selected, which cut every one of these figures.

Bank-level outages

Customers are spread across eight banks. An incident at one bank lifts the pooled failure rate by roughly an eighth of its severity, which is below the detection threshold. Pooling hides outages confined to a single bank.

200 customers, four windows, 8 populations. Share of outage windows detected.

Legal status

Whether a payment aggregator may lawfully use one merchant's transaction outcomes to schedule another merchant's debit for the same customer has not been established. Razorpay's merchant terms, their privacy policy and the relevant RBI directions have not been read. The repository records this as an open question.

07

External validation

There is no public benchmark for payment retry scheduling: no shared dataset, no held-out set, no leaderboard. The available comparisons are aggregate statistics published by companies selling recovery software. They are second-hand and they aggregate customer bases that are not comparable. The simulation is scored against four of them below.

Four published figures

The simulation is calibrated against a single anchor. None of the four below was used to set a parameter.

What was measured This world Published
Share of debits failing on their due date 10.50% 8–15% hit
Recovery under a fixed-interval retry schedule 22.15% 20–40% hit
Recovery under smart retry timing 95.24% 70–85% miss — too high
Share of recoveries landing inside 10 days 42.97% 85–95% miss — too slow

100 customers × about 2 mandates each, 120 days, at pop_spend=0.93 — the end of the plausible range whose due-date failure rate matches the published record. The four rows do not share a sample size. Rows one and two are properties of the world and of a policy this project did not write, measured on 100 populations with py -3.12 agent/tests/test_v3_power.py; the second clears its band's floor by 2.15 points against a 2 SE of 1.95. Rows three and four measure the agent, on 20 populations, with py -3.12 agent/tests/test_canonical_world.py --confirm. not gate-protected

The two matches

The two come from different parts of the model. The first measures the simulated world: how often an account is short on the due date. The second measures a baseline policy running inside it: what Razorpay's documented T, T+1, T+2, T+3 schedule recovers. Both fall inside their published bands at the same calibration.

The second row is also what answers the third. Both are measured in the same world, at the same calibration, with the same run seed. A world calibrated to be easy would lift both. The second lands in band and the third sits above it, so the excess belongs to the agent rather than to the world. That reading fails if the second row drops below 20% at a larger sample, or holds only at a calibration where the first leaves its own band.

The two mismatches

Recovery is too high because no simulated customer is permanently unable to pay: a clairvoyant schedule obeying the same four-attempt cap and notice rules collects 100% here, so that row measures the agent rather than the world. Recovery is too slow because a mandate's due date and its customer's payday are drawn independently, so the gap between them averages half a cycle. The same clairvoyant schedule reaches only 51.5% of failed debits inside ten days, below the published band's floor; the agent reaches 83.4% of that. The two rows have separate causes.

Alternative calibrations

Adding customers who cannot pay brings the third row inside its band, and so does adding temporary account holds. Both were swept, and both moved the first row outside its band. A grid search found a cell satisfying two targets at once; at that cell the two targets it had not been tuned against both moved outside their bands. Fourteen alternative calibrations have been swept and none scores better against the four figures than the one reported here.

Limits of this comparison: the published figures are vendor material rather than ground truth, and a simulation can reproduce an aggregate statistic while modelling the underlying mechanism incorrectly. Four figures is a small set; five further targets are specified but not yet implemented.

08

Scope

No Razorpay transaction, mandate or decline code has been observed by this project. All percentages and rupee totals here come from simulation. The simulation and the agent share an author, so the results are not independent evidence and should not be read as production estimates.

Simulated

  • Customer balances, salaries and spending
  • Payday timing
  • Every debit outcome
  • Outage windows and their severity
  • The merchant population
  • Every percentage and rupee figure here

From published sources

  • NPCI's five mandate execution rules
  • NPCI's decline code list and what each code means
  • Razorpay's 110 published error reasons
  • Razorpay's documented retry schedule (T, T+1, T+2, T+3, then halt)
  • The shape of Razorpay's Payment Downtime API

Not known

  • How often each decline reason actually occurs
  • How accurately payday can be predicted in India
  • Whether cross-merchant pooling is legally permitted
  • What fraction of debits fail during a UPI incident
  • Whether Razorpay's API accepts the recurring-charge request body written here. The client authenticates against the test API and reads successfully; charging requires an authorised mandate, which this project does not have

Limitations

  • The headline depends on two parameters. At ±1 and ±3 days of payday error the agent and the baseline are level; the +9.08 point figure is measured at ±7 days. It also depends on spending pressure: the difference runs +0.93 to +9.08 across the plausible range of household spending, and below the top of that range the world produces too few failed debits to measure a difference at all — two of them at pop_spend=0.80, across a thousand customers.
  • A fixed schedule matches the agent when payday is predictable. Two attempts placed at frozen offsets from the same payday estimate the agent is given collect 99.75% of at-risk cycles at ±1 day, against the agent's 98.59%. The agent is behind by 1.16 points there and by 0.33 at ±3, both inside the measurement error, and ahead by 1.15 at ±5, 3.55 at ±7, 23.83 at ±10 and 34.41 at ±14. It reaches that tie while spending about a quarter more attempts per cycle, 1.44 against 1.10, and recovering more slowly: 46.6% of at-risk cycles inside ten days against the fixed schedule's 49.9%. How accurately payday can be estimated in India is unmeasured, and Indian payroll practice — statutory payment by the 7th or 10th, most firms on the last working day, government salaries on a fixed date — points at the predictable end, where the fixed schedule is the simpler choice. The agent's advantage is protection against that estimate being wrong.
  • The headline batch runs with the richer decline taxonomy switched off, so it contains no frozen accounts, revoked mandates or limit hits. Switching it on costs between 0 and 13.5 points. Every rate in that sweep is unsourced.
  • The largest single sensitivity is an unsourced rate. How often a debit is refused by a transaction or mandate limit is not published anywhere. Sweeping it over 0.00 / 0.05 / 0.15 costs 0.00 / −2.29 / −9.22 points. The curve is non-linear, so the midpoint of the range is not the midpoint of the cost.
  • The timing score contains a hand-chosen discount factor. Sweeping it across a plausible range moves the headline by roughly 7 points.
  • Four of the simulation's twenty-five checks fail on a clean checkout. Each has a written reason recorded rather than a loosened threshold. Two are calibration gates that no parameter fixes; two are controls left failing so that a rewrite of the surrounding tests remains auditable.
  • Simulation results are not production estimates. The published industry benchmark for retry optimisation is a 6–8% uplift. The +9.08 point figure describes this simulated world at pop_spend=0.93.
  • Two of the four external checks are missed, and one of them cannot be hit on this rail. A clairvoyant schedule obeying the same four-attempt cap and notice rules reaches only 51.5% of failed debits inside ten days, against a published band of 85–95% drawn from card dunning. The agent reaches 43.0%, or 83.4% of what is available.
  • The study is small: 100 customers, about 2 mandates each, 10 populations for the batch figure and 20 for the external checks, one run seed each.
  • The single-customer walkthrough in section 01 is drawn from an earlier calibration of the same simulation, with 5 mandates per customer instead of about 2. It illustrates the mechanism. Every aggregate figure on this page comes from the current one.
